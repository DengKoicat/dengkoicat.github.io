这篇博客主要整理一下一个项目：面向直播电商中控质检的多智能体长视频理解系统。

场景很具体。自营和代播直播间每天有几百场带货直播，单场 2 到 6 小时，中控质检如果靠人工抽看，覆盖率不到 5%。但真正有业务风险的问题通常藏在几十秒片段里，比如极限词、价格误导、功效承诺、货不对板。平台处罚和客诉申诉又要求证据能精确到时间戳，所以系统不能只回答“有问题”，还要说明问题发生在哪个环节、哪段口播、哪一帧画面。

单个多模态大模型直接看整场直播并不稳。一方面是帧预算，几小时直播即使用几百帧均匀抽样，也很容易错过关键商品讲解或贴片画面；另一方面是跨时段关联，例如判断主播是否先抬价再降价，需要把相隔很久的几段口播和挂链页信息串起来。这个项目的核心思路是反过来：不让模型“看完整场”，而是让一组策略智能体先规划该看哪里，再用工具检索、浏览、定位证据。

整体上可以分成三块：

- **协作策略规划**：多个异构策略智能体各自生成工具调用计划，执行中共享中间证据，并根据同伴结果改写剩余计划。
- **多智能体强化学习**：先用自动标注的专家计划做策略 SFT，再用 GRPO 对整个智能体组做联合训练。
- **直播视频工具库**：把长视频理解拆成全局采样、事件检索、图像检索、粗浏览、细浏览、画面核验、时序定位等工具调用。

最后内部直播事件问答准确率从单智能体的 53.1 提到 74.5，违规审核推理一致率到 90.1，公开 LongVideoBench 做到 82.3。更关键的是，单视频平均只浏览 69.9 帧，端到端推理 19.8 秒，适合下播后的全量质检和客诉场景的在线问答。

## Collaborative Policy Planning

项目里的 agent 不是直接回答问题，而是先输出一份工具调用计划。可以把每个智能体看成一个独立质检员：拿到一个事件问句后，先判断需要哪些证据，再决定先检索哪段、浏览哪些帧、是否需要做时序定位。

比如问题是：

```text
主播讲解保温杯时，是否承诺过“全网最低价”？
```

一份典型计划是：

```json
[
  {"step": 1, "tool": "事件检索", "key_info": "保温杯讲解片段"},
  {"step": 2, "tool": "细浏览", "key_info": "价格相关口播与贴片文案"},
  {"step": 3, "tool": "时序定位", "key_info": "“全网最低价”话术出现的时间区间"}
]
```

这里最重要的是 `key_info`。它把问题里的取证目标显式传给工具：事件检索拿它当语义查询，图像检索拿它找贴片或商品特写，浏览模型拿它判断当前片段里应该看什么。

协作策略规划分成三个阶段：

```text
policy_generation
  -> policy_execution
  -> policy_communication
  -> policy_execution
  -> ...
```

- **策略生成**：每个智能体按问句和可用工具列表生成一份初始计划。
- **策略执行**：智能体按计划逐步调用工具，每一步的中间结果写入共享记忆。
- **策略通信**：智能体读取同伴中间结果，决定自己的剩余计划是否需要改写。

共享记忆可以简单理解成一个 per-agent 的 video memory buffer：

```python
from dataclasses import dataclass, field


@dataclass
class SharedMemory:
    initial_plans: dict = field(default_factory=dict)
    step_answers: dict = field(default_factory=dict)
```

每个智能体名下存两类东西：初始计划，以及每一步执行后的中间答案。中间答案不只是结论，还包括用了什么工具、看了哪些帧、找到哪些时间段和关键证据。策略通信读的就是这些记录。

这让计划可以动态改变。比如一个智能体原本想做全局采样，另一个智能体通过事件检索已经把“逼单促销”定位到第三小时附近，那么前者就可以把剩余计划从大范围浏览改成对该区间的细浏览和时序定位。这样既保留了多条取证路线的多样性，又避免所有智能体重复看同一个地方。

### Pipeline

简化后的主循环大概是这样：

```python
def cpp_pipeline(agents, video, question, options, toolkit, max_turns=5):
    memory = SharedMemory()
    tool_names = list(toolkit.keys())
    plans = {}

    for agent in agents:
        plan = agent.plan(question, tool_names)
        plans[agent.name] = plan
        memory.initial_plans[agent.name] = plan

    for _ in range(max_turns):
        for agent in agents:
            current_step = plans[agent.name][:1]
            answer = agent.execute(video, current_step, toolkit)
            memory.step_answers[agent.name] = answer

        for agent in agents:
            remaining_plan = plans[agent.name][1:]
            plans[agent.name] = agent.revise(
                question=question,
                toolkit=tool_names,
                memory=memory.step_answers,
                plan=remaining_plan,
            )

        if all(len(plan) == 0 for plan in plans.values()):
            break

    if options:
        return majority_vote(memory.step_answers.values())

    strongest = max(agents, key=lambda agent: agent.rank)
    return strongest.summarize(question, memory.step_answers)
```

多选题用多数投票，因为答案空间封闭，四个智能体各自给出选项后可以用共识抵消单个路线的错误。开放问答和时序定位没法直接投票，就由组内最强的 Qwen3-8B 读取所有中间证据做汇总。

这里没有给四个智能体预设固定分工。四个骨干分别是 Qwen3-8B、Qwen3-4B、Qwen2.5-7B、Qwen2.5-3B，规模和代际不同，计划风格天然有差异。大模型倾向于写更细的多步计划，小模型更直接，这种差异反而带来了互补。固定分工试过，但效果不如让分工在训练里自然形成，因为固定角色会把策略多样性框死。

## Tool Library

直播视频工具库把“看几小时视频”拆成“先检索，再聚焦浏览”。工具按用途可以分两组。

检索工具：

- **全局采样**：对整场直播均匀抽帧，适合概览类问题。
- **事件检索**：用 ASP-CLIP 把整场直播切成六等份，逐段计算和查询文本的语义相似度。
- **时间戳检索**：当客诉或处罚工单提供具体时刻时，直接截取前后一分钟片段。
- **图像检索**：用 ViT-CLIP-B/16 按 2FPS 建帧索引，匹配贴片文案、价格牌、商品特写等静态证据。

浏览与核验工具：

- **粗浏览**：Qwen3-VL-8B-Instruct 浏览 16 帧，快速判断候选片段是否相关。
- **细浏览**：Qwen3-VL-8B-Instruct 浏览 32 帧，用于价格数字、小字贴片、短暂画面等细节。
- **画面核验**：InternVL3.5-8B 核对画面商品、主播口播和挂链页信息是否一致。
- **时序定位**：Eagle2.5-8B 输出证据对应的起止时间区间。

事件检索和图像检索的粒度不同。事件检索是片段级，把几小时直播缩到几十分钟；图像检索是帧级，在候选片段里进一步找最相关的 16 或 32 帧。常见路径是：

```text
事件检索 -> 粗浏览 -> 细浏览 -> 时序定位
```

如果问题里有明确时间戳，则可以跳过语义检索：

```text
时间戳检索 -> 细浏览 -> 时序定位
```

画面核验是违规审核里很关键的一类工具。很多货不对板问题不是单看画面或单听口播能判断的，而是三方不一致：画面里举的是小样，主播讲的是正装；挂链页标的是临期批次，口播讲成正期；贴片写的是满减后价格，主播说成全网最低。把这个动作显式做成工具，比让单个多模态模型在一次前向里隐式完成稳定得多。

这套分层也让规划层和感知层解耦。四个策略智能体是纯语言模型，学的是计划、工具选择和通信改写；视觉语言模型在工具层负责看帧。以后替换更强的浏览模型或时序定位模型，不需要重训整个智能体组。

## Multi-Agent RL

只靠 prompt 能跑，但不稳。训练前的智能体常见问题有三个：计划格式偶尔不可解析，工具路线比较随意，通信阶段容易乱改计划。项目里用了两阶段训练：

```text
expert policy plan auto-labeling
  -> policy SFT
  -> GRPO joint training
```

### Policy SFT

公开视频理解数据有问句和答案，但没有现成的工具调用计划。做法是用 GPT-4o 和 DeepSeek-R1 组成一个自动标注团队，跑和线上类似的协作策略规划流程：生成计划、执行、通信改写，并记录完整轨迹。

标完后按两条准则筛选：

- 计划执行后得到正确答案。
- 计划不需要中途改写也能完整执行。

第二条很重要。一份计划如果靠反复改写才碰对答案，它的初始规划质量其实不好，拿来做 SFT 会把模型教偏。最终筛出约 8k 条高质量策略计划，用来让每个智能体先学会结构化输出和基本工具选择。

一条策略 SFT 样本大概是：

```json
{
  "video_id": "live_pub_000315",
  "task": "long_video_qa",
  "question": "这场直播里主播讲解保温杯时，是否承诺过'全网最低价'？",
  "options": ["A: 明确承诺过", "B: 只说过'优惠力度很大'未承诺", "C: 未提及价格对比"],
  "policy_plan": [
    {"step": 1, "tool": "事件检索", "key_info": "保温杯讲解片段"},
    {"step": 2, "tool": "细浏览", "key_info": "价格相关口播与贴片文案"},
    {"step": 3, "tool": "时序定位", "key_info": "'全网最低价'话术出现的时间区间"}
  ],
  "gold_answer": "A",
  "annotator_team": ["GPT-4o", "DeepSeek-R1"],
  "keep_reason": "答案正确且计划无需改写"
}
```

SFT 阶段的目标很收敛：不是让模型学会完整协作，而是让它先稳定地产出合法计划。协作和路线偏好留给后面的强化学习。

### GRPO

强化学习阶段优化的是整个组的协作策略。对同一个问题，每个智能体采样 $K$ 份候选计划，执行后得到候选最终答案和协作轨迹。每条轨迹计算一个复合奖励，再在组内做相对优势标准化。

整体 rollout 可以写成：

$$
\tau_i = (p_i, e_i, c_i, y_i), \quad i=1,\ldots,K
$$

其中 $p_i$ 是初始计划，$e_i$ 是工具执行过程，$c_i$ 是通信改写轨迹，$y_i$ 是最终答案。工具本身不回传梯度，它们是环境的一部分；模型学习的是计划文本、关注焦点和通信改写决策。

奖励函数由三项组成：

$$
R(\tau)=R_{\mathrm{ans}}(y, y^*) + R_{\mathrm{format}}(p) + R_{\mathrm{col}}(\tau)
$$

答案奖励是主信号：

$$
R_{\mathrm{ans}} =
\begin{cases}
1, & y = y^* \\
-1, & y \ne y^*
\end{cases}
$$

格式奖励很小，只负责保证计划可解析：

$$
R_{\mathrm{format}} =
\begin{cases}
0.2, & p \text{ is valid} \\
-0.2, & p \text{ is invalid}
\end{cases}
$$

协作奖励由 LLM-as-judge 给二值分，判断整条轨迹是否连贯、工具调用是否恰当、改写是否有依据：

$$
R_{\mathrm{col}} =
\mathbb{I}[\text{trajectory is coherent}]
- \mathbb{I}[N_{\mathrm{tool}} > 5]
$$

这里对超过 5 次工具调用的轨迹重罚，是项目里很关键的一个修正。早期协作奖励刚加上去时，智能体发现多调用几次工具、把轨迹写长，更容易被评审模型判为“连贯”。结果平均计划长度从三步涨到七八步，效果没有涨，推理成本先翻倍。加入工具调用次数重罚后，计划长度一个训练周期内回到三步以内。

GRPO 的优势来自组内标准化：

$$
\hat{A}_i = \frac{R_i - \mu_R}{\sigma_R + \epsilon}
$$

其中：

$$
\mu_R = \frac{1}{K}\sum_{j=1}^{K}R_j,\quad
\sigma_R = \sqrt{\frac{1}{K}\sum_{j=1}^{K}(R_j-\mu_R)^2}
$$

训练目标可以写成带 KL 约束的 clipped policy objective：

$$
\mathcal{J}_{\mathrm{GRPO}}(\theta)=
\mathbb{E}\left[
\frac{1}{K}\sum_{i=1}^{K}
\frac{1}{|p_i|}
\sum_{t=1}^{|p_i|}
\min\left(
r_{i,t}(\theta)\hat{A}_i,
\mathrm{clip}(r_{i,t}(\theta),1-\epsilon,1+\epsilon)\hat{A}_i
\right)
-\beta D_{\mathrm{KL}}(\pi_\theta \parallel \pi_{\mathrm{ref}})
\right]
$$

其中：

$$
r_{i,t}(\theta)=
\frac{\pi_\theta(a_{i,t}\mid s_{i,t})}
{\pi_{\theta_{\mathrm{old}}}(a_{i,t}\mid s_{i,t})}
$$

这里选 GRPO 而不是 PPO，主要是为了省掉 critic。PPO 要为每个智能体维护价值网络，四个异构骨干就会变成四套 critic，训练成本和调参复杂度都上去；而多智能体环境里的 value 估计本来就不稳。GRPO 用同一问题下的候选计划互为 baseline，对这个场景更自然。

训练时还做了 agent dropout：每个训练步从全连接通信图里随机采样一个有向无环子图，作为本轮通信拓扑。也就是说，有些智能体在某些步骤收不到部分同伴的中间结果。这样可以防止小模型完全依赖 Qwen3-8B，逼着每个智能体既能协作，也保留独立取证能力。

### Training Setup

智能体组由 Qwen3-8B、Qwen3-4B、Qwen2.5-7B、Qwen2.5-3B 四个异构骨干组成，规划层合计约 22B 参数；结合工具库里的视觉模型后，总参数规模约 37B。

训练配置：

| 阶段 | 配置 |
| :--- | :--- |
| 策略 SFT | 1 epoch，batch size 32，learning rate $1\times10^{-6}$ |
| GRPO | 200 steps，4 rollouts，batch size 8，learning rate $1\times10^{-7}$ |
| KL 约束 | $\beta=1\times10^{-5}$ |
| 长度限制 | prompt 1024，generation 1024 |
| 交互上限 | 最多 5 轮工具调用 / 通信 |
| 训练栈 | AdamW，DeepSpeed stage 2，Flash-Attention，bfloat16，8 张 A100 80G |

GRPO 的学习率设得很小，是因为 SFT 后模型已经会生成合法计划，强化学习只需要微调路线偏好和协作行为；学习率太大反而会破坏格式能力。多智能体环境的奖励方差也更高，同一个问题下的候选奖励会受同伴行为影响，小学习率加 KL 约束更稳。

项目还做了 LoRA 对照：rank 8、alpha 16、dropout 0.05、learning rate $2\times10^{-6}$，只更新约 2% 参数，LongVideoBench 做到 81.2，比全参微调的 82.3 低 1.1 个百分点。主链路用全参版本，因为违规审核是核心业务；LoRA 保留为新品类快速适配和资源紧张时的低成本选项。

## Data

数据分成四块：

| 数据集 | 用途 | 类型 | 规模 |
| :--- | :--- | :--- | :--- |
| 公开视频理解数据 | 策略计划自动标注 | 视频问答 / 时序定位 / 空间理解 / 视频推理 | 约 10.3 万条实例 |
| 自标注策略计划 | 策略 SFT | Policy-Plan | 约 8k 条计划 |
| 内部直播间录像库 | 领域适配与评测 | Live-Video | 约 1.2 万条直播切段 |
| 违规口播与画面标注 | 违规判定金标 | Violation-Annotation | 约 3.1 万事件段 |
| 讲解与高光时段标注 | 时序定位金标 | Temporal-Grounding | 约 1.8 万 query |

公开视频数据负责让策略能力泛化。只用问答类数据，模型会学到很单一的计划模式；混合时序定位、长视频问答、空间理解、视频推理后，模型更容易根据问题类型选择工具组合。

内部直播数据来自自营和代播直播间中控存档，覆盖开场引流、商品讲解、逼单促销、答疑互动四个环节。违规金标由中控质检和平台合规岗双人复核，标注内容包括违规类型、发生环节和证据时间窗。价格和优惠类问题以挂链页快照为事实标准，因为口播本身可能就是违规来源，不能拿口播当真值。

数据隔离也很关键。内部数据按场次级别隔离，同一场直播的切段不会同时进入领域适配和评测；同一主播同一商品的相邻场次也排除，避免话术雷同造成变相泄漏。公开视频侧，策略标注数据和 LongVideoBench、Video-MME、Video-Holmes 这些评测基准在数据源上不重叠。

## Evaluation

内部评测分四类任务：

| 评测集 | 实例数量 | 平均视频时长 | 任务类型 |
| :--- | ---: | :--- | :--- |
| 直播事件问答 | 1000 | 约 9600 秒 | 整场直播多选问答 |
| 违规口播审核 | 600 | 约 10200 秒 | 违规类型与发生环节判定 |
| 货不对板画面核验 | 500 | 约 8400 秒 | 商品、口播、挂链页一致性 |
| 讲解时序定位 | 800 | 约 9000 秒 | 讲解与违规话术时间区间定位 |

指标也对应业务目标：

- **Accuracy**：事件问答和画面核验的主指标。
- **Violation-Agreement**：模型对违规类型与发生环节的判定，与平台合规岗复核结论的一致比例。
- **m-IoU**：预测时间区间和金标时间区间的平均交并比。
- **推理开销**：单视频平均浏览帧数和端到端时延。

m-IoU 的计算是：

$$
\mathrm{IoU}([s_p,e_p],[s_g,e_g]) =
\frac{\max(0,\min(e_p,e_g)-\max(s_p,s_g))}
{\max(e_p,e_g)-\min(s_p,s_g)}
$$

对整个评测集取平均：

$$
\mathrm{mIoU}=\frac{1}{N}\sum_{i=1}^{N}\mathrm{IoU}_i
$$

比如金标是 3312.0 到 3390.5 秒，预测是 3300.0 到 3395.0 秒，IoU 约为 0.7877。这个指标比“命中片段就算对”更严格，因为边界偏移也会扣分。

内部直播评测结果：

| GPT-4o | 59.3 | 71.2 | 42.8 | - |
| Gemini 1.5 Pro | 60.9 | 72.5 | 46.3 | - |
| Qwen2.5-VL-72B | 63.4 | 74.8 | 48.9 | 51.6 |
| 本方案（22B 组 + 工具库） | 74.5 | 90.1 | 70.2 | 63.4 |

相对单智能体，四项任务分别提升 21.4、23.1、22.6、21.9 个百分点，提升幅度很一致。相对 Qwen2.5-VL-72B，本方案在事件问答和画面核验上分别领先 11.1 和 21.3 个百分点。这里的优势不主要来自参数量，而来自关键片段覆盖和结构化取证流程。

### Ablation

训练与奖励组件消融：

| 变体 | LongVideoBench | Video-Holmes | Δ LongVideoBench |
| :--- | ---: | ---: | ---: |
| 去掉策略 SFT（仅 GRPO） | 80.2 | 57.9 | -2.1 |
| 去掉 GRPO（仅 SFT） | 75.9 | 55.2 | -6.4 |
| 去掉协作奖励 $R_{\mathrm{col}}$ | 81.1 | 59.4 | -1.2 |
| 去掉格式奖励 $R_{\mathrm{format}}$ | 82.0 | 60.2 | -0.3 |
| 去掉 agent dropout | 79.9 | 58.5 | -2.4 |

GRPO 是最大杠杆。去掉后 LongVideoBench 掉 6.4 个百分点，说明协作能力主要是联合强化学习学出来的。agent dropout 掉 2.4，说明随机通信拓扑对防止过度耦合很重要。格式奖励只贡献 0.3，但它能减少不可解析计划，提升训练效率和线上稳定性，所以仍然保留。

汇总机制也做过对比：

| 决策机制 | LongVideoBench | Video-Holmes |
| :--- | ---: | ---: |
| 各智能体互评打分取最高 | 81.2 | 59.9 |

## Deployment

线上分两条链路。

第一条是下播后的批处理质检。每场直播结束后，系统按质检题库跑事件问答和违规审核，输出违规清单、违规类型、发生环节和证据时间戳。第二天中控质检员不再从头看录像，而是复核模型给出的短清单和对应片段。

第二条是客诉和临时排查的在线问答。输入是具体问题，系统只对检索到的候选片段做浏览和汇总，十几秒到几十秒出结果。客服拿到的不是一句结论，而是带时间戳和截图证据的回答，用于回复用户或准备平台申诉。

违规审核的业务偏好和普通准确率不完全一样。漏报一次违规可能带来平台处罚，误报则只是多一条人工复核。因此审核链路的阈值更偏召回，可疑就报，再由合规岗终审消化误报。事件问答和高光切片没有这种不对称成本，就按准确率和边界质量优化。

灰度也按风险推进。先在自营三个直播间跑违规审核链路，模型初审和人工终审并行四周，用改判率作为线上指标；离线一致率和线上改判率趋势对上后，再放量到全部自营，最后接入代播。代播涉及客户店铺，风险更高，所以放在最后。

## Lessons

这个项目里最有价值的经验不是“多智能体一定更强”，而是多智能体必须有可训练的协作接口。只把几个 agent 用 prompt 绑在一起，很容易变成昂贵的投票器；真正带来增益的是计划、执行、通信和汇总这几个环节都被结构化，并且能通过奖励信号优化。

几个具体结论：

- **先检索再浏览比长上下文更重要**。几小时直播里，关键证据通常只有几十秒，均匀抽帧很浪费预算。
- **异构比同构更适合协作**。不同骨干会生成不同取证路线，多样性比单纯堆参数更有用。
- **SFT 和 GRPO 解决的问题不同**。SFT 让计划合法，GRPO 让协作有效，两个阶段都不能省。
- **奖励不能只鼓励“看起来合理”**。LLM-as-judge 的协作奖励必须配合工具调用次数约束，否则模型会刷长轨迹。
- **工具层要可替换**。策略模型只学习决策，视觉理解模型作为环境工具存在，这样后续升级感知模型不会牵动整个训练链路。

当前短板也比较明确。时序定位 m-IoU 63.4 已经能做初审取证，但高光切片的入点出点仍然需要人工精修；系统现在主要支持下播后批处理和在线问答，还没有做到直播进行中的实时预警；音频线索利用也不充分，语气、背景音乐、观众互动节奏这类信息还没有专门建模。

整体看，这个项目更像是把 Agentic RL 放进一个非常具体的业务闭环里：长视频不是直接塞进模型，而是变成可检索、可浏览、可验证的环境；智能体不是只生成答案，而是学习如何调用工具、共享证据、控制成本。这个思路在直播质检之外，也适合很多“证据分散、工具多、结果要可追溯”的场景。
